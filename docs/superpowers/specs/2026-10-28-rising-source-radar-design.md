# 급상승 소재 레이더 (rising source radar) — 설계

- 날짜: 2026-10-28
- 브랜드: cosmicpath (국내 Threads). cosmicpath-global은 범위 밖.
- 바탕: `docs/superpowers/specs/2026-10-27-reference-replay-design.md` (v2, 키워드 TOP 신호만). 이 문서는 그 위에 얹는 **증분 설계**다. 거기서 정한 것 중 여기서 바꾸지 않은 것은 그대로다.
- 표기: **[사용자 결정]**은 대화에서 사용자가 정한 것, **[내 판단]**은 설계자가 정한 것으로 빌더가 근거를 갖고 바꿀 수 있다.

## 1. 왜 만드나

- 2026-10-28 경쟁 분석: 달빛 연구소 "스레드 레이더"(radar.dalbitai.com, 베타·테스터 5명)는 키워드별로 15초마다 남의 글을 감시해 반응 속도가 빠른 글을 찾고, 그 사연을 AI가 분석해 창작 소재로 넘겨준다. 반응 수는 스크래핑으로 얻는 것으로 보인다(공식 API는 남의 글 반응 수를 주지 않는다).
- 우리에게 같은 루프의 80%가 이미 있다: `viral` 크론(하루 2회 키워드 TOP 수집, `referenceScore`) → `refill` 크론(평소 07:13 1회, 길이 실험 중에는 15:13·23:13 포함 3회. 하루 1개 `ref_replay` 초안). 모자란 건 두 가지다.
  1. **느리다.** 글이 21:41에 처음 잡히면 두 번째 확인이 다음날 09:41, 자격은 그 뒤 첫 refill에서. 첫 발견 → 초안이 **평소 약 34시간, 실험 중 3회 refill로도 최대 17.5시간**. 글 반응은 첫 48시간에 붙으므로 소재로서 늦다. 실험용 refill 2회는 실험 끝나면 빠지므로 34시간이 기준선이다.
  2. **소재를 안 가져온다.** 현재 `ref_replay` 프롬프트는 "구조만 따르고 주제·소재·문장은 새로 써"다. 사용자가 원하는 건 **뜨는 글을 바로 분석해 그 사연을 소재로 글을 쓰는 것**이다. **[사용자 결정]**
- 안 하는 것(사용자가 경쟁 분석에서 걸러낸 것): 댓글 선점·자동 댓글, 스크래핑, 남의 사연 웹툰화. **[사용자 결정]**

## 2. 목표 / 비목표 / 실패 조건

**목표**
1. 첫 발견 → `ref_replay` 초안까지 **12시간 이내**(지금 34시간). **[내 판단: 하루 안이면 "뜨는 중"에 올라탈 수 있다]**
2. "지금 올라가는 중"인 글을 우선 고른다. 순위 상승·여러 키워드 동시 등장·발행 시각이 최근인 글. **[내 판단]**
3. 원글의 **상황(사건)과 감정선**은 가져오고, 인물·표현·문장·고유 디테일은 새로 쓴다. 원글 작성자가 읽어도 자기 글이라고 못 알아보는 수준. **[사용자 결정: "상황+감정선"]**
4. 전부 기존 부품(`viral` 크론, `ViralExample.rawMetrics`, `refillReferenceReplay`, `REFERENCE_REPLAY_MODE`, 유사도 검사)의 재조립. 새 테이블·새 화면·새 라이브러리 없음.

**비목표**
- 분 단위 감시, 알림(텔레그램 등), 사람이 댓글 달러 가는 흐름. 결과물은 **큐에 들어간 초안**이지 알림이 아니다.
- 글 단위 좋아요·조회수. 공식 API가 주지 않는 건 추측하지 않는다(v2 그대로).
- `ref_replay` 하루 상한 변경. 1개 유지. **[내 판단: 하루 5슬롯 중 1개가 남의 소재인 건 이미 받아들인 선, 더 늘리면 계정 색이 흐려진다]**
- 쇼츠 레이더, 트렌드 레이더 변경.
- DB 스키마 변경.

**실패 조건 (작동해도 실패로 본다)**
- 발행된 글에 원글 문장이 한 줄이라도 남거나, 원글의 고유 디테일(지명·직업·숫자·이름)이 그대로 들어간 것.
- 같은 원글(같은 `sourceKey`)로 초안이 두 번 만들어진 것.
- 하루에 `ref_replay`가 2개 이상 생성된 것(v2 실패 조건 그대로).
- 수집 주기를 올렸는데 Threads API 한도나 GitHub Actions 한도에 걸려 **평소 수집까지** 멈춘 것.
- 한 번만 TOP에 스친 글이 원본이 된 것(`timesSeen ≥ 2`는 유지).

## 3. 설계

### 3.1 수집 주기: 하루 2회 → 4시간마다 6회

- `viral.yml` cron을 `41 0,12 * * *` → `41 */4 * * *`(KST 01:41, 05:41, 09:41, 13:41, 17:41, 21:41). **[내 판단: 4시간이면 발견 후 다음 확인까지 최대 4h, "두 번 잡힘" 자격이 4h 만에 충족된다]**
- 비용: 키워드 10개 × 6회 = 하루 60회 `keyword_search`. v2의 20회에서 3배. 공식 한도는 **사용자당 24시간 롤링 2,200회**(2026-10-28 Meta 문서 확인, 결과 0건인 호출은 미집계)라 3% 수준. GitHub Actions는 하루 6분 안팎.
- Claude 분석(`analyzeTopViralExamples`)은 "미분석 행 중 최근 30개 → 상위 5개"인데, 한 번 수집에 최대 100행이 들어와 미분석 행은 거의 항상 남는다. 즉 6회로 늘리면 **매 실행 5건, 하루 30건**이 된다. `ref_replay` 생성은 분석 결과(`whyItWorks`)를 쓰지 않고 본문만 쓰므로 빠른 경로에 분석은 필요 없다. 따라서 **분석은 처음부터 09:41·21:41 두 실행에만 묶는다**: 라우트에 `analyze` 쿼리(기본 `true`, 하위 호환)를 두고, `viral.yml`에서 `github.event.schedule`이 추가 4회 중 하나면 `analyze=false`로 호출한다. **[내 판단, 빌더 체크 반영]**
- `MIN_SEEN_AGE_MS`를 11h → **3h**(4h 간격 − 지연 여유 1h). `MIN_TIMES_SEEN = 2`는 유지. 주석의 근거("하루 2회 실행 기준")를 새 주기로 고친다.

### 3.2 급상승 신호: 순위 이력과 `risingScore`

지금은 재수집 때 `searchRank`·`keywordHits`가 **최신값으로 덮어써져** 상승인지 하락인지 모른다. 이력을 남기고 상승분을 점수에 얹는다. 전부 `rawMetrics` JSON 안, 스키마 변경 없음.

- `rawMetrics.rankHistory`: `[{ at: ISO, rank: number, hits: number }]`. 수집마다 1건 추가, **최근 12건(48h)만 유지**. `mergeStoredRawMetrics`가 `PERSISTED_RAW_KEYS`처럼 이 키를 이어받아 append 한다. **[내 판단: 배열 상한을 두어 행 크기가 자라지 않게]**
- **같은 글이 키워드별로 다른 행**(`source: keyword:<kw>`, 같은 `sourceKey`)에 저장되고, 어느 행이 갱신되는지는 실행마다 다르다. 그래서 `rankGain`·`freshness`는 **저장 시점에 행에 박지 않고, 선택 시점에 `sourceKey` 그룹의 `rankHistory`를 합쳐 계산**한다. `pickReferenceReplaySource`가 이미 `sourceKey`로 묶어 max를 보므로 그 자리에 얹는다. 행 단위로 하면 "이전 최고 순위"가 키워드 하나에 갇히고, 재수집 안 된 행의 신선도가 썩는다. **[내 판단, 빌더 체크 반영]**
- `risingScore = referenceScore(그룹 max) + rankGain × 3 + freshness` — 선택 시점 계산값, 저장하지 않음.
  - `rankGain`: 그룹 이력 전체에서 **이전 최고 순위 − 현재(가장 최근) 순위**, 0 미만은 0. (5위 → 2위면 +9)
  - `freshness`: `publishedAt`이 지금 기준 24h 이내 +15, 48h 이내 +5, 그 외 0.
  - 가중치는 상수 + 주석. 3·15·5는 `calculateSearchSignalScore`의 순위 1단계 = 3점에 맞춘 값이다. **[내 판단]**
- `pickReferenceReplaySource`는 정렬 키를 `referenceScore` → **`risingScore`** 로 바꾼다. 자격 조건은 그대로. 대시보드에 보이려면 같은 함수로 계산해 보여준다(선택).
- 이 점수도 v2처럼 **추측**이다. 6장 판정이 검증이다.

### 3.3 즉시 초안: `viral` 크론 끝에서 `refillReferenceReplay` 호출

- `/api/cron/viral`이 브랜드별 수집·분석·학습을 마친 뒤 `refillReferenceReplay(brand, now)`를 **한 번 더 호출**한다. 함수 안의 게이트(오늘 0개, 큐에 대기 0개, 오늘 시도 0개, 키워드·ownHandle 있음)가 이미 하루 1개를 보장하므로 **게이트 코드를 추가하지 않는다**.
- `refill` 크론의 기존 호출은 **그대로 둔다**. `viral`이 먼저 만든 날은 `already_today`로 스킵되고, `viral`이 자격 있는 글을 못 찾은 날은 07:13에 전처럼 시도한다. 두 경로 모두 같은 함수라 상한이 깨질 길이 없다.
- 응답 JSON에 `referenceReplay` 결과를 넣어 수동 실행(`workflow_dispatch`) 때 보이게 한다.
- `maxDuration 300s` 안에 수집 + 분석 + 생성 1개가 들어가야 한다. 생성 1개는 refill에서 이미 같은 예산 안에 돌고 있으니 가능하다고 본다. 넘치면 생성을 먼저(수집 직후, 분석 전) 돌린다. **[내 판단]**

### 3.4 프롬프트: "구조만" → "상황+감정선"

`REFERENCE_REPLAY_MODE`(id `ref_replay`)의 지시문과 규칙을 바꾼다. id·label은 유지. **[내 판단: 새 id를 파면 `resolveViralIntentMode`·refill 게이트·출처 태그 조회 세 곳이 갈라지고, 기존 `ref_replay` 글이 "쓴 원본" 집계에서 빠져 같은 원글이 재사용될 수 있다]**

- instruction: "아래 참고 글의 **상황(무슨 일이 있었는지)과 감정의 흐름**(예: 황당 → 찔림 → 체념)을 가져와, cosmicpath 독자가 자기 일처럼 느낄 새 글을 쓴다. 구조(첫 줄 방식, 줄 구성, 마무리)도 참고하되 그대로 베끼지 않는다."
- rules:
  1. "참고 글의 문장·표현을 그대로 옮기지 않는다." (유지)
  2. "등장인물·관계·지명·직업·숫자·이름 같은 **고유 디테일은 전부 바꾼다.** 원글 작성자가 읽어도 자기 이야기라고 못 알아봐야 한다." (신규)
  3. "감정선은 가져오되 결론·시선은 cosmicpath(사주·궁합·타이밍)로 가져온다. 원글의 결론을 반복하지 않는다." (신규)
  4. "본문은 140~260자를 목표로 한다." (유지)
- **프롬프트 문구는 두 곳이다.** 모드 외에 `generate-posts.ts`의 참고 글 헤더(`[참고 글: 다른 계정에서 반응이 좋았던 글. 구조만 따르고 주제·소재·문장은 새로 써]`)가 하드코딩돼 있어 **같이 바꾼다**: "다른 계정에서 반응이 좋았던 글. 상황과 감정의 흐름을 가져오되 인물·표현·문장·고유 디테일은 새로 써". 모드만 바꾸면 헤더와 모순된다. **[빌더 체크 반영]**
- **상황의 출처를 하나로 만든다.** 모든 글은 매트릭스에서 `[주제]`·`[타겟 독자]`·`[상황/맥락]`을 랜덤 배정받는데, `ref_replay`는 상황을 참고 글에서 가져와야 하므로 프롬프트에 상황이 둘 들어가게 된다. 그래서 `referenceReplay`일 때는 `[상황/맥락]`을 매트릭스 값 대신 **"참고 글의 상황을 쓴다"** 한 줄로 치환한다. `[주제]`·`[타겟 독자]`는 매트릭스 그대로 둔다. 주제는 결론을 끌고 갈 cosmicpath 각도(궁합·타이밍·이직 등)이고, 상황은 참고 글에서 오는 사건이라 역할이 겹치지 않는다. `recentSituations` 포화 검사는 매트릭스 상황에만 의미가 있으므로 `ref_replay` 글은 그 검사와 `recentSituations` 집계에서 뺀다. 이로써 `generate-posts.ts`의 experiment 조립(`buildExperiment`)과 프롬프트 조립 두 곳이 수정 범위에 들어온다. **[내 판단, 빌더 체크 반영. 근거: 사용자가 "소재로 글쓰기"를 정했으므로 상황은 참고 글의 것이어야 한다]**
- 기존 유사도 검사(`checkAntiRepeatSimilarity` + `REFERENCE_COPY_REASON` 드롭)는 그대로. 규칙 2를 코드로 검사하지는 않는다(LLM 규칙 + 유사도 검사 + 6장 사람 검수). **[내 판단: 고유명사 추출 검사는 과잉. 첫 20개를 사람이 보고 문제면 그때]**
- 전환 시점을 기록한다: 이 변경이 배포된 날짜 이후 `ref_replay` 글만 6장 판정 표본이다. 그 전 글은 "구조만" 세대.

### 3.5 바뀌지 않는 것

발행 경로, 품질 게이트, 길이 실험 격리, 출처 태그(`ref_replay_source:<id>`), 제외 계정, 경보, 킬 스위치(`keywords` 비우기), 대시보드. 대시바드 바이럴 목록에 `risingScore` 칸 하나 보이는 건 **선택**(빌더 재량, 안 해도 됨).

## 4. 제약

- 공식 Threads API만. 남의 글 반응 수 없음. 스크래핑 없음. **[사용자 결정]**
- 스키마 변경 없음(승인 절차 회피가 아니라, 필요가 없다).
- 새 라이브러리 없음.
- `ref_replay` 하루 1개, 길이 실험 표본 격리(v2 그대로).
- Meta 비원본 콘텐츠 정책: 문장 재사용 0%, 고유 디테일 교체.

## 5. 빌더에게 맡기는 것

- `rankHistory` append와 `risingScore` 계산의 정확한 함수 위치(`viral-analysis.ts` vs `reference-radar.ts`). 기존 `calculateReferenceScore` 옆이 자연스럽다.
- `rankGain`의 "이전 최고 순위" 정의가 키워드별인지 전체인지. **기본은 전체**(어느 키워드든 가장 좋았던 순위). 키워드별이 더 맞다고 보면 바꾸되 주석에 이유.
- `viral` 라우트에서 `refillReferenceReplay`를 분석 전에 둘지 후에 둘지(3.3의 시간 예산 판단). 라우트의 brand `select`가 축소돼 있어 `refillReferenceReplay(brand: Brand)`에 맞게 전체 행을 읽어야 한다.
- 테스트: `pickReferenceReplaySource`에 "risingScore가 referenceScore 순서를 뒤집는 경우" 1건, `mergeStoredRawMetrics`에 "rankHistory 12건 상한" 1건, `buildExperiment`에 "ref_replay는 상황 치환 + 포화 검사 제외" 1건, 프롬프트 규칙 변경은 기존 모드 테스트 갱신. 그 이상은 불필요.

|---|---|
| `ref_replay` 프롬프트의 "상황"이 매트릭스 것인지 원글 것인지 | **원글.** 3.4에 상황 치환·포화 검사 제외를 명시. 사용자 결정("소재로 글쓰기")에서 답이 나온다. |
| Claude 분석을 처음부터 2회 실행에만 묶을지 | **묶는다.** 3.1 수정. 빠른 경로는 분석을 안 쓴다. |
| 지연 기준선 34h가 틀림(실험 중 refill 3회) | 1장 수정. 평소 34h, 실험 중 17.5h. 실험 끝나면 34h로 돌아가므로 3.3은 그대로 필요. |
| 참고 글 헤더가 `generate-posts.ts`에 하드코딩 | 3.4에 "두 곳 같이 수정" 추가. |
| `rankHistory`를 행 단위로 쌓으면 키워드별로 이력이 쪼개짐 | 3.2 수정. 저장은 행 단위, 점수는 선택 시점에 `sourceKey` 그룹 합산. |

## 6. 판정 (언제 성공·실패로 보나)

전환 배포 후 **`ref_replay` 20개 발행** 시점에 한 번.

| 지표 | 출처 | 통과 |
|---|---|---|
| 지연 | `ViralExample.rawMetrics.firstSeenAt` → `Post.createdAt` | 중앙값 ≤ 12h |
| 효과 | `ref_replay` 20개 조회수 중앙값 vs 같은 기간 일반 글 중앙값 | ≥ 1.3배 (v2와 같은 기준) |
| 안전 | 20개를 사람이 원글과 나란히 읽음 | 원글 문장·고유 디테일 잔존 0건 |
| 비용 | 주간 `keyword_search` 호출 수, Claude 분석 호출 수 | 한도의 50% 이하 |

- 효과 미달이면: 주기는 두고(비용 작음) 프롬프트를 "구조만"으로 되돌리거나 상황만 가져오는 중간 선으로 조정.
- 안전 1건이라도 걸리면: 즉시 "구조만"으로 되돌리고 규칙 2를 코드 검사로 올린다.

## 7. 경쟁 대비 포지션 (참고)

달빛 레이더는 "소재 찾기 도구"(사람이 보고 행동), 우리는 "발행 운영 도구"(초안이 큐에 들어옴). 같은 사람(스레드 키우는 1인 사업자)을 보지만 우리는 API 범위 안에서 멈춘다. 저쪽의 분 단위 감시·반응 수는 스크래핑 의존이라 따라가지 않는다. 이 설계가 가져온 건 **"지금 뜨는 글을 소재로"** 라는 한 아이디어뿐이다.
